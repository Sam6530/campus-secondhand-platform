# 提交要求对照与维护责任

本文件依据《学生需求分析与AI智能体使用验证报告 提交材料说明》整理，只规定提交要求、字段和维护责任，不代表活动已经执行。原说明中的业务示例不作为本项目需求。原说明与本对照存在差异时回查原说明；不同于实际参与者后续明确调整的交付范围时，记录差异，不能悄悄当作已满足。

所有成员必读，与共同大纲、协作协议及格式规范一起使用。c统合质量报告、总证据索引与交付清单，d主责AI报告和独立复核；a/b及其他产出者按下表供稿。正文引用材料的编号、位置和最终版本。

## 总提交要求

单独提交需求规格说明书、需求分析质量验证报告、AI智能体使用验证报告，另附业务依据、模型可编辑源与清晰导出、原型材料、实际走查/验证证据以及关键AI任务的实际交互和上下文。Markdown便于协作；提供Word时同时提供同版PDF，注明最终版本、提交日期和配套文件。

AI交互附件保留任务背景、输入材料及版本、关键原文提示词与输出、实际发生的追问反馈及后续调整，定位到任务号、证据号和具体轮次。完整对话可放附件，正文引用关键片段；原说明没有要求必须采用截图，截图也不能替代模型源文件。未留存不补造。若本轮明确跳过记录，交付时如实说明该要求未覆盖，不把简略使用概况称为完整满足。

## 需求规格说明书正文结构补充

按正文结构建议的八部分组织为：项目概述、用户需求、领域与数据、规则与权限、行为与状态、质量要求、验收与验证、基线与人机协作。章节及分工以共同大纲v3.1为准。图表可放附件，但正文标明编号和具体位置并保留必要说明。

需求清单覆盖全部必做范围；详细用例建议3至5个代表性闭环，复杂度需要可增加。每例记录编号名称、参与者、触发、前置、主/替代/异常流程、成功失败结果、关联规则、验收标准及预期使用频率或触发规律；频率缺依据标待确认，不编造。

关键数据字典记录含义、来源、约束、责任人或维护角色、隐私属性及访问规则；无需提前规定所有数据库字段类型、索引和实现类。权限矩阵同时覆盖角色与对象范围。质量要求包含情境、可观察指标、检验方法，以及数值与取舍的依据或待确认状态。

基线部分能定位已确认范围、未决问题、关键人工决定、AI使用和任务约束；实际人机过程详见AI报告。约束、迭代、变更及风险并入相应部分，不遗漏也不另写重复报告。

### A.2 确认口径

来源性质为原始资料、AI候选、分析推导。确认状态按实际活动登记为业务方已确认、教师已确认、团队已复核或待确认，不要求所有记录经过全部确认类型。学生扮演业务人员/用户/教师时记录实际学生、模拟角色、日期、讨论依据和结论，并标“教学模拟”；不等同真实业务方或任课教师认可。

确认由实际参与学生作出，AI角色回答不构成学生确认。未确认数值保持候选，不能因写进图、表、原型或测试而升级。存在争议时说明负责人、影响及确认前处理。真实确认与教学模拟分别说明。

### A.3 图模型口径

选择实际涉及的模型，不要求把清单中的图全部画一遍。上下文图表达边界与交互；用例图表达参与者和目标关系；活动图表达起止、交接、分支和异常；领域类图表达类、属性、关联和基数，多模块说明共享与跨模块关系；状态图表达状态、事件、条件及执行者；若使用目标树，表达目标层级和成功指标。符号必须符合声称的模型类型。

复杂条件可移到配套表，通过编号关联；图与术语、数据字典、规则、权限、质量指标和其他模型保持一致。只有聊天截图不构成可编辑模型交付。

### A.4 状态与拒绝

状态变化的记录在图上标转换号；状态保持的记录可在图注或配套说明关联。当前状态和目标状态同名时注明状态保持，不能称成功转换；拒绝说明提示、业务数据及状态是否变化。条件引用规则号并沿用其确认状态；变更同步用例、权限和验收场景。

### A.5 场景记录

每个场景记录：SC号、名称与类型、目标情境、初始数据/状态、走查方式、依据及版本、实际参与者及分工/日期、关联需求/用例/规则、状态图和转换号。实际人员分工与步骤中的业务角色分开。

逐步表字段：步骤、角色、操作、预期系统响应、涉及数据/状态及转换号、发现问题。覆盖正常、权限、状态转换、异常四类；无状态变化的步骤不强行关联转换。未提供转换表时在场景中补清事件、条件、执行者、结果及失败处理。

本组自走查、跨组交叉走查、AI反向走查是原说明建议方式；教师抽查以条件允许为前提，不写成每种方式都必须完成。实际开展哪种就记哪种，AI发现只是候选意见。推演符合预期不等于业务认可，也不等于原型操作或功能验证。

### A.6 原型与PV记录

原型记录：名称/类型/版本、入口/启动方法/环境、可走查页面或核心功能、模拟数据/接口范围、未实现与未验证限制、复用SC号、AI任务号、实际执行者及日期。纸面原型提供页面与查看顺序，可点击界面提供访问和操作说明，简化程序提供运行方式。

PV逐项记录：编号及关联需求/SC、实际操作与具体输入、预期、实际结果、问题、结论及证据位置，按需引用BR/ST。复用SC的情境及预期，另记本次操作观察；不把推演结论复制成实测结果。已实现功能须实际执行并核对数据和状态。

结论为通过、失败或未验证，并写范围，如页面流程、模拟交互或功能验证。已开展无问题写“无”，未开展写“未验证”。AI自动执行与学生人工观察分别注明，AI日志不替代原说明要求的人工实际观察。失败项记录修改位置和复验；新问题回到需求、规则、场景及模型更新。开发阶段可引用同版系统及已有测试/验收记录。

### A.7与A.8 闭环与责任

同一问题沿用一个V号，汇总SC/PV等发现依据。处理为修改、保留、暂缓，写理由及责任人；已修改未复核标待复核，不能只写已处理。复核检查修改及相关影响，处理者和复核者分别登记；尚未解决说明剩余影响、责任人和下一步。未检查不写未发现问题。

贡献按四人分别记录实际工作，不能复制相同笼统描述。可包括访谈、查证、建模、原型、测试、评审及整合，说明人工核查、采纳/拒绝AI建议及理由。每人应能解释产物、关键判断及实际验证方法，AI不作最终确认者。

### B.1 工具信息

阶段填需求分析或开发/迭代；使用方式按问答辅助、智能体执行等实际情况填写。模型或版本不清楚时写“未记录”，不猜测，不把问答改写成自主执行。

### B.2 关键任务与结论

建议选3至5段影响重要判断的交互，数量不是硬性指标。同一任务可有多个片段，同一证据可支持多个要求；不强制多轮追问或人工否定。没有追问写未发生，采纳建议也说明理由；未核验明确写未核验。

任务记录字段：任务号/名称/关联编号；操作者/审核者/日期；目的、输入版本及必要上下文；实际关键提示词；AI实际输出或动作及原始位置；人工质疑与风险检查；实际追问及调整；独立核验方法、范围、核验者、结果及证据；人工决定/决定者/理由；最终处理、需求影响及产物位置；未解决问题。人工决定为采纳、部分采纳、拒绝或保留待确认。

核对同源生成、过度补全和伪一致性等风险。无问题也说明核对对象、方法和接受理由；AI自检和另一AI的意见仅是线索，不等于业务确认或实际功能验证。人工采纳不改变事实/规则确认状态；确认口径沿用A.2。

关键结论另记：结论、性质、依据、核验状态与结果。性质区分事实陈述、推断、假设、建议；事实陈述不表示已证实，建议的评估与采纳分别说明。可写入任务案例或用结论号引用，不必另建重复文件。正文自然表达，分析材料中的性质分类必须保留。

### B.3 适用条件与任务约束

原说明规定：课程未布置B5时，本节写“不适用”；已布置时，提交一个实际使用过的任务约束示例，说明执行结果与必要改进。B5是否布置尚不清楚时，由实际成员核查课程安排，不根据仓库无代码、无记录或AI猜测直接判不适用。

只有约束设计而未使用，标“边界设计，未执行”；不能冒充实际使用。需求阶段可选补用例、模型或一致性检查，无需提前做架构或业务代码。

记录类型为边界设计或实际执行，关联AI任务号。字段包括：任务目标与关联需求；输入材料/阅读要求及版本；允许范围；禁止范围；输出形式及业务规则；人工确认责任；信息不足处理；完成标准与验收方法；实际执行与检查结果及证据；必要约束改进及理由。无需改进也说明依据。可引用B.2/B.4，不重复复制。

### B.4 索引与附件

每份证据一个E号，可被多个任务、需求、成员引用。索引字段为证据号、类型/内容、原件或有权限的链接及具体段落/轮次/版本、支持的任务/需求/记录。可引用走查、验证、问题和贡献材料；上下文足够理解任务，完整记录留存备查。附件可访问，与最终版本一致，移除密码、令牌及无关个人敏感信息。
